# Worker-side Neon Prisma adapter (not deployed)

A separate `generated/prisma-worker/` (Prisma 6.19.3, `engineType = client`) is constructed with `@prisma/adapter-neon@6.19.3`. The `createWorkerNeonPrisma` factory is isolated from the Node/SQLite runtime and requires an injected Worker `env` with exact Staging/Production Worker name, known Neon project ID, tier billing mode, and a TLS-enabled Neon PostgreSQL URL. The function has no network activity on module import or Client construction; requests must explicitly invoke it and subsequently disconnect.

The `NEON_PROJECT_ID` binding alone is not proof of target-database identity: it is caller-supplied metadata. Runtime URL validation now pins each tier to its verified **Neon compute hostname** (or that hostname's exact `-pooler` variant) recorded in `config/deployment/environments.json`, preventing a correctly labeled Staging Worker from connecting to a Production endpoint and vice versa. Port and TLS policy are validated before Prisma construction. Compute rotation requires verifying the replacement Neon endpoint in the connected infrastructure account and updating the reviewed manifest; do not weaken the guard to allow arbitrary `.neon.tech` hosts. Constructor tests use fake credentials and **make no network queries**.

Project identities are publicly named deployment contract metadata, not credentials. The Worker environment's `NEON_PROJECT_ID`, `VSN_WORKER_NAME`, `SHOPIFY_BILLING_TEST_MODE`, and `DATABASE_URL` must be set **separately per protected Cloudflare Worker** and verified against actual Neon endpoint evidence before any app runtime is enabled.

This is an SDK/client foundation only. Real Neon connectivity, token/session correctness, Shopify's Node adapter replacement, server-side streaming, worker bundling, signed session acceptance, and recovery checks still require implementation. No Neon/Cloudflare worker secrets were read or deployed. A one-time write-enabled GitHub Actions workflow successfully regenerated the exact Prisma 6.19.3 Neon adapter lockfile, passed reproducible npm installation, production dependency audit and no-network constructor tests, and was removed immediately afterward. Remaining jobs use read-only permissions.
